## Architecture Decisions

- Starter-template import crosses the Liveblocks room boundary via a lightweight `TemplatesProvider` context. Reason: the navbar lives in `editor-shell` (outside `RoomProvider`) but the import must mutate the room's `useLiveblocksFlow` state. The shell owns `isTemplatesOpen` and exposes `{ isOpen, close }` through context; `FlowCanvas` (inside the room) consumes it, mounts the modal, and runs the import where the collaborative state is reachable. React context passes through `RoomProvider` normally, keeping the established "shell owns state, canvas updates state" pattern intact.
- Template import replaces the canvas through `onNodesChange`/`onEdgesChange` `remove`+`add` changes, not `setNodes`/`setEdges`. Reason: `useLiveblocksFlow`'s return value only exposes `onNodesChange`/`onEdgesChange`/`onConnect`/`onDelete` (no direct setters), so clearing then adding via change events is what keeps the replacement on the Storage-synced collaborative path. `fitView` runs inside a `requestAnimationFrame` so it measures after the new nodes mount.
- Both editor sidebars float *over* the canvas (`absolute inset-y-0` inside a `relative ... overflow-hidden` stage) rather than participating in the layout flow. Reason: the canvas must read as an edge-to-edge infinite surface (Figma/Excalidraw feel) with the dotted background visible beneath the panels; a flex layout would shrink the canvas and box it in. The stage's `overflow-hidden` doubles as the clip that fully hides each sidebar when it translates off-screen, so there is no peeking sliver to manage with exact pixel offsets.
- React Flow `<Background>` / `<MiniMap>` are themed via component color props (hex matching the design tokens) rather than Tailwind classes. Reason: these are SVG-driven library widgets that only accept color *values* (not class names), so the same "transported value" exception used for cursor colors applies — the dark hex values mirror the `globals.css` tokens (`#080809` base, `#2a2a30` border, `#111114` surface).

- The canvas surface is split across small files: `canvas-room.tsx` (Liveblocks providers + suspense/error scaffolding), `flow-canvas.tsx` (React Flow + `useLiveblocksFlow` + drop handling), `canvas-node.tsx` (custom node renderer), `shape-panel.tsx` (drag source), and `canvas-error-boundary.tsx`. Reason: keeps the `"use client"` boundary on the canvas only (the page stays a server component), and isolates the Liveblocks wiring from the React Flow rendering so each layer can evolve independently (custom edges, cursors, persistence) without a monolithic component.
- `useLiveblocksFlow` is the single source of truth for nodes/edges — there is no local `useState`/`useNodesState`. Reason: the hook is backed by Liveblocks Storage (key `"flow"`), so consuming its `nodes/edges` + change handlers directly is what makes the canvas collaborative. New nodes are added through `onNodesChange([{ type: "add", item }])` rather than a separate setter, so the mutation flows through the same Storage-synced path.
- `CanvasNodeData` is declared as a `type` (object literal), not an `interface`. Reason: React Flow's `Node<Data extends Record<string, unknown>>` constraint accepts object-literal type aliases (which get an implicit index signature) but rejects interfaces, so `CanvasNode = Node<CanvasNodeData, "canvasNode">` only type-checks when the data is a `type`.
- The Liveblocks room is wrapped with a hand-rolled `CanvasErrorBoundary` (a 25-line class component) instead of adding the `react-error-boundary` dependency. Reason: the spec only needs one connection-error fallback around `ClientSideSuspense`; `getDerivedStateFromError` covers that without a new package. The skill's `react-error-boundary` example can be swapped in later if multiple granular boundaries are needed.
- `initialPresence` is `{ cursor: null, isThinking: false }`. Reason: the `Presence` type in `liveblocks.config.ts` requires both `cursor` and `isThinking`, so even though the spec only mentions `cursor: null`, `isThinking` must be seeded to satisfy the type. No `initialStorage` is passed — `Storage` is `Record<string, never>` and `useLiveblocksFlow` lazily creates its own `"flow"` `LiveObject`.
- React Flow dark theming uses `colorMode="dark"` rather than per-component hex props. Reason: it applies React Flow's built-in dark palette to the background, minimap, and handles in one prop, avoiding hardcoded hex values in component styling (consistent with the project's "tokens, not hex" rule). Node fill/text colors are still concrete hex because they are transported node *data* (the same exception as cursor colors).
- New-node IDs are `${shape}-${Date.now()}-${counter}` where `counter` is a per-canvas `useRef`. Reason: `Date.now()` alone collides when several shapes are dropped within the same millisecond; the monotonic ref guarantees uniqueness without pulling in a UUID dependency, and the shape prefix keeps IDs human-readable.
- The shape drag payload travels under a custom mime type (`application/ghost-ai-shape`) rather than `text/plain`. Reason: it scopes the drop handler to this app's shapes so unrelated text drags onto the canvas are ignored (`getData` returns `""` → early return).
- Drop handling lives on the wrapper `<div>` outside `<ReactFlow>`, which forces `FlowCanvas` to wrap `FlowCanvasInner` in `<ReactFlowProvider>`. Reason: `screenToFlowPosition` (via `useReactFlow`) is only available inside the React Flow context; the provider exposes it to the wrapper that owns the `onDrop` handler.

- Liveblocks auth uses **access tokens** (`prepareSession` → `session.allow` → `session.authorize`), not ID tokens. Reason: the spec asks the route to "return a session token with user name, avatar, generated cursor color" — access tokens attach `userInfo` directly to the returned session token and grant room access in the same call, which maps cleanly onto the single-room-per-project model. ID tokens would push permission management entirely onto `getOrCreateRoom` defaults/usersAccesses and add a second concern to the route. Membership is still verified first via `getProjectAccess`, so the token is only ever issued to an owner or collaborator.
- The room is ensured with `getOrCreateRoom(room, { defaultAccesses: [] })` (private), and access is granted by the **session token**, not by room default/user accesses. Reason: with access tokens the authoritative permission is the token's `session.allow(room, FULL_ACCESS)`; leaving `defaultAccesses: []` keeps the room closed to anyone without a server-issued token, so the Clerk + `getProjectAccess` gate remains the single source of truth for who can join.
- Room ID == project ID (consistent with the Feature 07 "project ID == Liveblocks room ID" decision). The auth route reads `body.room` (Liveblocks' default client payload) and passes it straight to `getProjectAccess`, so a `403` is returned for any room the caller does not own or collaborate on.
- `lib/liveblocks.ts` exposes a `getLiveblocks()` accessor that constructs the client lazily and caches it on `globalThis`, rather than a top-level `export const liveblocks = ...` like `lib/prisma.ts`. Reason: `DATABASE_URL` is set at build time so the eager Prisma construction is safe, but `LIVEBLOCKS_SECRET_KEY` is not yet provisioned; an eager throw would break `next build` when the route module is imported during page-data collection. Deferring construction to the first request keeps the client cached without coupling build success to a runtime-only secret.
- Cursor colors come from a fixed hex palette in `lib/cursor-color.ts`, not from `globals.css` design tokens. Reason: cursor colors are user metadata serialized into the Liveblocks token and rendered by Liveblocks' own cursor primitives, not Tailwind-class-driven UI — they need concrete color values at the data layer, which is outside the "no hardcoded hex in styling" rule (that rule governs component class names, not transported data).
- Collaborator invites use `upsert` rather than `create` so the API is idempotent. Reason: the UI cannot easily distinguish "already invited" from "newly invited" without an extra round-trip, and the spec collapses both into the same successful outcome ("invite collaborators by email"). Repeated invites stay safe and the dialog can blindly POST without pre-checking.
- Collaborator `DELETE` is also idempotent — `prisma.projectCollaborator.delete` is wrapped in `.catch(() => undefined)` so deleting an already-missing row still returns `204`. Reason: the dialog optimistically refreshes from its own state after a successful delete; a stale row that the DB already lost should not surface as an error to the user.
- Collaborator GET uses `getProjectAccess()` (owner *or* collaborator allowed) but POST/DELETE re-derive ownership directly from `prisma.project.findUnique({ select: { ownerId } })`. Reason: read access intentionally extends to collaborators per spec ("collaborators can view the collaborator list only"), while write access is owner-only — and POST/DELETE only need the owner id, not the project name, so a narrower `select` keeps the mutation path lean.
- Emails are normalized (`trim().toLowerCase()`) on every boundary — `POST /collaborators` body, `DELETE` URL segment, and the Clerk lookup. Reason: `ProjectCollaborator.email` is part of the composite primary key; without consistent casing, `User@Example.com` and `user@example.com` would collide on insert or fail to match on delete. Normalization happens in a single helper (`normalizeCollaboratorEmail`) so the dedup contract isn't duplicated across routes.
- Clerk lookup failures degrade silently to email-only rows rather than failing the entire `GET /collaborators` request. Reason: the share dialog is the only place that surfaces collaborator presence; if Clerk is briefly unavailable, owners must still be able to see who they invited and remove them. Both the outer `clerkClient()` await and each per-batch `users.getUserList` call are try/catched, mirroring the spec's fallback rule ("if a Clerk user is not found for an email, fall back to showing the email only").
- The share dialog uses `canManage = currentProject?.ownership === "owner"` rather than re-asking the API. Reason: `ownership` is already known at the layout level (computed by `lib/projects.ts` for each entry in `ownedProjects` / `sharedProjects`); the dialog UI is purely a permission-display concern, while the *real* enforcement happens server-side in POST/DELETE. Threading the API ownership response into the UI would add a fetch dependency without any new security guarantee.
- `ShareDialog` is mounted in `EditorShell` (sibling of the projects sidebar), not inside `ProjectsProvider`. Reason: the share dialog needs the *currently active* project (from path lookup), not the global owned/shared lists; `ProjectsProvider` exists to host project-list-level dialogs (create/rename/delete) that operate on arbitrary projects. Keeping the share dialog at the shell level avoids muddling those concerns and keeps the navbar's `onOpenShare` callback wired to local shell state.
- Workspace access is enforced inside `/editor/[roomId]/page.tsx`, not in `proxy.ts` or the layout. Reason: `proxy.ts` only knows about Clerk auth; it can't see project ownership without an extra Prisma round-trip on every middleware run. Putting the check inside the page keeps middleware fast (auth-only) and lets the page render `AccessDenied` instead of redirecting — which matches the spec's "non-owner / missing project shows AccessDenied" rule rather than the "unauthenticated → /sign-in" rule.
- `getProjectAccess` treats "project missing" and "user not authorized" identically: both return `null`. Reason: the spec collapses them into the same UI surface (`AccessDenied`), and exposing a distinct "not found" path would leak project existence to non-members.
- `currentProject` is derived in the client via `usePathname()` + lookup against the layout-fetched project lists, rather than threaded through props from the page. Reason: the navbar lives in the editor *layout* (so the sidebar and chrome stay mounted across navigations), but the layout can't see route params for nested routes — pages cannot push data up to parent layouts in Next.js App Router. Since `ownedProjects` + `sharedProjects` are already loaded at the layout level and every accessible room id is present in one of them, looking up the active project by id in `EditorShell` keeps the navbar/sidebar in sync without a duplicate fetch.
- The AI sidebar is conditionally mounted on `currentProject != null` rather than always rendered with zero-width. Reason: the `/editor` empty-state page should not show the AI chrome at all, and conditional mounting also keeps any future hooks/state inside `AiSidebar` from running on routes where it's irrelevant.
- Project rows in the sidebar are `<Link>` elements, not buttons. Reason: the sidebar is the only navigation surface to switch rooms once a user is inside a workspace; wrapping the title block in a Link gives free middle-click/cmd-click support, makes the row crawlable for back/forward, and lets the active row use `aria-current="page"` semantics.

- Project ID == Liveblocks room ID. The client generates `${toSlug(name)}-${suffix}` (6-char `[a-z0-9]` suffix via `crypto.getRandomValues`) before calling `POST /api/projects`. Reason: the spec for Feature 07 explicitly requires "project ID and Liveblocks room ID should stay aligned" — generating the id client-side and letting the API store it verbatim means the same value can be reused as the Liveblocks room id later without a second lookup. `parseProjectId` validates the format server-side; if the client omits the id, Prisma's `cuid()` default still applies (defense-in-depth for non-UI callers).
- Editor data is fetched in `app/editor/layout.tsx`, not the page. Reason: the sidebar lives inside `EditorShell` (rendered by the layout) and needs both lists; pages cannot push data up to the layout in Next.js. Fetching in the layout means every editor route gets the lists for free, while the page itself stays a small server component that delegates the only client interaction (`openCreate`) to `NewProjectButton`.
- `lib/projects.ts` is marked `import "server-only"` and queries Prisma directly rather than calling `GET /api/projects`. Reason: the API route requires Clerk's session and would force the server component into a fetch-against-self pattern with auth replay; using Prisma directly inside the already-authenticated layout is both simpler and faster.
- `useProjectActions` consolidates dialog state, the create-suffix, and the API mutation calls in one hook. Reason: the previous split (`useProjectDialogs` + provider-owned mutation callbacks) made sense when mutations only touched in-memory mocks. Once mutations need `router.push` / `router.refresh` and the create flow needs a stable suffix tied to the dialog lifecycle, owning all of that in a single hook avoids ferrying `router` instances through the dialog component or recreating suffixes on every render.
- Delete navigation uses `pathname` (from `usePathname`) to detect whether the deleted project is the currently-open workspace. Reason: the spec requires "redirect to `/editor` if deleting the active workspace, otherwise refresh"; pathname matching against `/editor/${id}` and its sub-routes is the lightest way to distinguish the two cases without threading the active project id through React context.
- API routes (`/api/*`) are excluded from `auth.protect()` in `proxy.ts` and instead enforce authentication inline (`await auth()` → explicit `401` JSON response). Reason: middleware's `auth.protect()` redirects unauthenticated browser requests to `/sign-in` and uses `notFound()` for non-document requests, neither of which matches the spec contract that API clients receive `401 { error: "Unauthorized" }`. Page routes still use middleware protection.
- API ownership checks happen inside each handler: `prisma.project.findUnique({ select: { ownerId: true } })` is run first, returning `404` if the row is gone and `403` if `ownerId !== userId`. This pattern is shared across `PATCH` and `DELETE` so the spec's distinction between "not found" and "non-owner mutation" stays clear (rather than collapsing both into `404`).
- Project create defaults `name` to `"Untitled Project"` when the request omits it or sends an empty string. Reason: spec rule "default missing project name to `Untitled Project`". The fallback is applied **after** `parseProjectName` trims input, so whitespace-only names also trigger the default rather than persisting blank values.
- `lib/prisma.ts` types the export as `PrismaClient` (not a union of base + Accelerate-extended client). Reason: Prisma's `$extends` widens the generic type signature so the union of "bare client" and "extended client" is not assignable to a single callable shape — `prisma.project.findUnique(...)` fails type-checking. Casting the Accelerate branch back to `PrismaClient` keeps the runtime extension active for the Accelerate URL while exposing the standard Prisma surface to consumers. If Accelerate-specific methods (`cacheStrategy`, etc.) are needed later, introduce a separate typed export instead of widening the base.
- Prisma 7 client is always constructed with a driver adapter (`@prisma/adapter-pg`'s `PrismaPg`) — Prisma 7 throws when `new PrismaClient()` is called without arguments, so the adapter is required even in the Accelerate branch. The Accelerate branch additionally chains `.$extends(withAccelerate())` from `@prisma/extension-accelerate` to opt the client into Accelerate's caching/extension surface. Type is then cast back to `PrismaClient` (see preceding decision).
- `ProjectCollaborator` uses a composite primary key (`@@id([projectId, email])`) instead of a synthetic `id` column. Reason: spec required a unique constraint on `(projectId, email)` plus "no extra fields unless required by Prisma" — composite PK satisfies both the uniqueness constraint and Prisma's primary-key requirement without adding a column.
- Project list, dialog state, and dialog rendering all live in a single `ProjectsProvider` mounted inside `EditorShell`. Reason: both the `/editor` empty-state page (rendered as `{children}`) and the floating sidebar need to trigger the same dialogs over the same in-memory list. Lifting state up to the provider keeps the dialog instances mounted once and prevents stale state when the sidebar opens/closes. Dialogs are rendered as siblings of `{children}` so Radix portals from the same root regardless of trigger origin.
- The dialog hook (`useProjectDialogs`) takes mutation callbacks (`onCreate / onRename / onDelete`) instead of owning the project list. Reason: the hook is a presentation-state primitive (open/close, form value, submitting flag) that can later be wired to a real API or Prisma mutation by swapping the callbacks — no churn inside the dialog components.
- Sidebar item actions (rename/delete) are gated by passing `onRename`/`onDelete` props per row. The Shared tab calls `<ProjectList>` without them, so collaborator projects never render the affordances. Reason: spec requires hiding actions for shared projects; gating by prop presence keeps `ProjectRow` reusable without an extra `ownership` branch.
- Mobile sidebar dismissal uses a tap-to-close backdrop scrim (`md:hidden`, `bg-black/50`) rendered as a sibling of the `<aside>`, fading in/out with the same transition. Reason: the floating sidebar overlays content rather than pushing it, so there is no off-canvas region to detect outside-taps against.
- Clerk's `afterSignOutUrl` is set to a **public** route (`/sign-in`) at the `ClerkProvider` level. Reason: `proxy.ts` protects `/` via `auth.protect()`, and Next.js 16's RSC fetch on a soft sign-out navigation does not survive a middleware-driven redirect to `/sign-in` — it fails with `TypeError: Failed to fetch` and falls back to a hard browser navigation. Pointing sign-out directly at the public route keeps the sign-out path on a single, soft navigation with no middleware redirect in the middle.
- shadcn/ui generated files in `components/ui/*` are treated as protected foundation components per `ai-workflow-rules.md` — not modified after install.
- Theme tokens are defined as CSS custom properties in `app/globals.css` and exposed to Tailwind via `@theme inline`, per `ui-context.md`. shadcn's variables (`--color-background`, `--color-primary`, etc.) are aliased to project tokens so primitives blend with the project dark theme.
- Dark only: `:root` declares `color-scheme: dark` and there is no `.dark` class scope or light fallback.
- Route-protection is via `proxy.ts` at the project root (Next.js 16 renamed `middleware.ts` → `proxy.ts`). All routes are protected by default; only Clerk's sign-in/sign-up paths (resolved from `NEXT_PUBLIC_CLERK_SIGN_IN_URL` / `NEXT_PUBLIC_CLERK_SIGN_UP_URL`) are public.
- Editor chrome lives under `app/editor/*`, not the root layout. The root layout is reserved for global concerns (fonts, `ClerkProvider`, base body styles) so unauthenticated routes like `/sign-in` and `/sign-up` render without the navbar / project sidebar.
- Clerk appearance is configured once in `lib/clerk-appearance.ts` and consumed by `ClerkProvider`. Color overrides are expressed as `var(--…)` references — never hex / rgba — so the Clerk widgets stay in lockstep with `globals.css` tokens.

Node deletion also cascades to incident edges to avoid orphans. React Flow's built-in deletion is disabled via `deleteKeyCode={null}`.
- **Connection handles**: handles get `zIndex: 3` so all four (top/right/bottom/left) sit above the shape body and reliably capture the connection pointerdown — previously the shape fill swallowed the non-top handles.

## Canvas delete + connection fixes (2026-07-04)

- **Shared delete path (`canvas-delete-context.tsx`)**: a single `deleteElements(nodeIds, edgeIds)` handler now lives in `FlowCanvasInner` and is exposed to the node/edge renderers via `CanvasDeleteProvider`. It cascades edge removal for deleted nodes and routes everything through the Liveblocks `onNodesChange`/`onEdgesChange` helpers so all clients stay in sync. Both the keyboard shortcut and the new inline delete buttons call it — one source of truth.
- **Backspace/Delete moved to a `window` keydown listener** (was an element `onKeyDown` on the wrapper `<div>`, which only fired when focus happened to sit inside it). The window listener still bails on editable targets (input/textarea/contentEditable) and only acts when something is selected. This is why deletion appeared broken before — the wrapper div was rarely the focus root.
- **Inline delete buttons**: the node color toolbar (`ColorToolbar`) gained a divider + trash button that deletes the selected node. Edge deletion uses React Flow's official `EdgeToolbar` (`@xyflow/react` v12.11) — it portals to the edge layer and auto-shows while the edge is selected, positioned just above the edge center (`alignY="bottom"`) so it never overlaps the label pill. Replaced the earlier hand-rolled `×` button inside `EdgeLabelRenderer`. Both node and edge buttons call the shared `deleteElements`.
- **Edge-to-node connection fix**: `connectionRadius={55}` on `<ReactFlow>` so releasing a connection anywhere over a node latches onto its nearest handle (previously only a ~20px radius around the tiny 8px handle dot registered, so drops on the node body silently failed). Additionally, `CanvasNodeRenderer` reads `useConnection((c) => c.inProgress)` and reveals every node's handles while a connection is being dragged (opacity was 0 on non-hovered targets, and hover never fires mid-drag because the pointer is captured) — so users can see and aim at the drop targets.
- **Floating edges (`floating-edge-utils.ts`)**: adopted React Flow's official floating-edge pattern to fix ugly orthogonal loops. Pinning an edge to one fixed handle (top/right/bottom/left) makes `getSmoothStepPath` route around a node whenever the connected handle faces away from the other node — the wider `connectionRadius` made this worse by snapping to far-side handles. `CanvasEdgeRenderer` now calls `useInternalNode(source/target)` and `getEdgeParams()` to recompute each endpoint as the point on the node border facing the other node (with the matching `Position`), ignoring the stored `sourceHandle`/`targetHandle`. Result: connections always attach cleanly at any angle, and the large snap radius is now safe (a "wrong" handle no longer produces loops). Falls back to the handle coordinates React Flow provides if a node isn't measured yet. The 4 handles are kept purely as drag-out / drop targets for creating connections.
- **Shape-aware floating edge endpoints**: `floating-edge-utils.ts` now reads each node's `data.shape` and computes the endpoint against the visible shape outline (rectangle, circle/ellipse, pill, diamond, hexagon, and cylinder inset) instead of treating every node as its outer bounding box. Edge side selection is now based on the endpoint direction from the node center, so diamond/hexagon side intersections no longer fall back to `Position.Top` and make smooth-step edges appear offset from the node. `CanvasEdgeRenderer` types `useInternalNode` as `CanvasNode`, and CSS-rendered nodes now reveal handles while any connection is in progress, matching the SVG node behavior.
- **Reliable side-handle drops for connections**: connection creation no longer depends on a large `connectionRadius` around tiny source-only handles. Each node now keeps the four visible side handles as source handles and adds matching target handles with the same ids while connecting from another node. React Flow stays on `ConnectionMode.Strict`, `connectionRadius` is reduced to `20`, and `isValidConnection` rejects self-connections. This fixes side-handle drops that previously failed or stored target ids with no matching target handle.
- **Handle id parity for edge creation**: the invisible `body-target` surface was removed from the new-connection path because React Flow stores concrete `targetHandle` ids such as `top`, `right`, `bottom`, and `left` when users connect side handles. `CanvasNodeRenderer` now renders matching `source` and `target` handles for all four side ids, with target handles accepting pointer events only while connecting from another node. This fixes React Flow error 008 (`Couldn't create edge for target handle id`) for both user-created side-handle edges and starter-template/imported edges with null handles. A hidden `body-target` target handle remains only for backwards compatibility with older saved canvases.
- **Drop position**: node is centered on the cursor by offsetting `screenToFlowPosition` by half the node size (the drag ghost is cursor-centered).
- **Auto-zoom on first drop removed**: dropped the `fitView` prop from `<ReactFlow>` (it fired a deferred fit when the first node hit an empty canvas). Fit-on-load is now explicit in the load effect only.
- **Clerk avatars**: `next.config.ts` allows `img.clerk.com` via `images.remotePatterns`.
- **UserButton** now renders only on the editor home navbar (hidden when `isWorkspace`).
